## Screens / components

### Enrollment page — passkey section (NEW section on the existing page)

- **Route:** `GET user/two-factor` (name `two-factor.settings`, existing) — `auth/two-factor-settings.blade.php`, rendered after the existing TOTP branch block in every state **except** the recovery-codes once-display.
- **Components:** `x-ui.card` titled "Passkeys" →
  - Empty state: one reassuring line ("No passkeys yet — a passkey lets you sign in with your fingerprint, face, or device PIN instead of an authenticator app.") + label `x-ui.field` ("Passkey name", help: "Something you'll recognize, like *iPhone* or *Office security key*.") + `x-ui.button` primary "Add a passkey" (wired by `passkey.js`; without WebAuthn support the button renders disabled with the line "This browser doesn't support passkeys — the authenticator app above works everywhere.").
  - With passkeys: one row per credential — label (semibold), "Added <fmtDate> · Last used <fmtDate(updated_at)>" in muted text, `x-ui.button` secondary `size="sm"` "Revoke" inside a DELETE form (`passkeys.destroy`). Revoke is behind the existing password-confirmation gate; the consequence line sits under the list: "Revoking a passkey removes it immediately. If it's your only way past two-factor, you'll be asked to set up again at your next sign-in."
  - Setup-mode state: the section appears under the restricted-session banner unchanged; copy in the section header notes "Either path completes setup — passkey or authenticator app." (C-01: both paths offered.)
- **JS:** `@vite(['resources/js/passkey.js'])` — the "Add a passkey" flow (options → `navigator.credentials.create()` → store → follow the JSON `redirect`). Ceremony errors surface in an inline `role="alert"` line in the card ("That didn't complete — check that this device can create a passkey, then try again."), never a stack trace, never a silent no-op.
- **Mockup section:** `#s-passkeys`.

### Challenge page — passkey section (NEW section on the existing page)

- **Route:** `GET two-factor-challenge` (name `two-factor.login`, existing) — `auth/two-factor-challenge.blade.php`, rendered **only when the challenged user has ≥1 passkey** (`$hasPasskey`).
- **Components:** above the TOTP form: heading adapts — "Use your passkey, or enter a code" when a passkey exists (TOTP-only users see the 005 heading byte-identical) → `x-ui.button` primary "Use a passkey" (fingerprint glyph, ≥44px) wired by `passkey.js`; the existing "or" divider separates it from the code form; the recovery-code form is unchanged.
  - Failure: the JS shows the same generic sentence the code form uses, in the same error slot style — "That didn't work. Try again, or use a recovery code." (005-D05, contract §Ceremonies step 6). No reason is ever shown.
  - Unsupported browser: the button is replaced by muted text "Passkeys aren't available in this browser — use your code below."
- **Mockup section:** `#s-challenge-passkey`.

### Copy rules

- Never "WebAuthn", "FIDO", "attestation", or "credential" in user-facing copy: it's a **passkey**, the gesture is "fingerprint, face, or device PIN", the list is "your passkeys".
- One primary button per view (UI_Standards door): on the challenge page the passkey button is primary when present and the TOTP submit becomes secondary; on the enrollment page the existing primary stands and "Add a passkey" is the passkey card's primary-in-card (mirrors how the 005 fresh state primaries its card action).
