| 2026-10-08 | 008-D02 | **O-02 resolved — recovery codes ARE issued at passkey confirmation.** When a user's first passkey is stored and `two_factor_recovery_codes` is null, the app generates 8 single-use codes in Fortify's exact format (encrypted JSON in the same column, via the same `RecoveryCode::generate()`), flashes them for the existing once-display on the enrollment page, and the existing challenge POST accepts them for passkey-only users (Fortify's `validRecoveryCode()` never required a TOTP secret — verified in vendor source) | Brief O-02: a passkey-only admin who loses their device needs a self-serve break-glass; council had to decide before Plan | Require a second passkey (no help when the lost device was the only one and the user ignored the advice); another admin resets them via the 004 invitation machinery (not self-serve, and a sole org_admin has no peer); no recovery at all (account loss = org loss — unacceptable for the owner account) | Passkey-only users get the identical break-glass shape as TOTP users (8 codes, shown once, never re-displayed — 005-D03 applies unchanged). Codes are issued only when the column is null, so TOTP users see no second set. Audit: `mfa.passkey.registered` payload carries no code material (AuditLogger blocklist forbids `recovery`-named payload keys — the issuance is recorded by the event `mfa.passkey.recovery_codes.issued`) | [D] |
| 2026-10-08 | 008-D03 | **O-03 resolved — RP ID comes from environment configuration, never code.** Laragear's published `config/webauthn.php` reads `WEBAUTHN_ID` / `WEBAUTHN_ORIGINS` from env. Tests pin `WEBAUTHN_ID=localhost` + `WEBAUTHN_ORIGINS=http://localhost` in `phpunit.xml` and drive ceremonies with a deterministic virtual authenticator. Real-device enrollment gates on the production domain (rollout gate, not a build gate) | Brief O-03: WebAuthn credentials are origin-bound; browsers refuse ceremonies from the IP-literal dev URL (`172.235.37.44:3100`) | Hardcode the dev host (breaks the moment a domain exists, and silently invalidates every enrolled passkey when it changes); skip RP config until production (then the test suite can't pin it either) | The build and all 11 verdicts are fully provable now; flipping `WEBAUTHN_ID` at domain launch is a config change. Freeze checklist gains one item: real-device smoke test on the production domain before passkeys are advertised | [D] |
| 2026-10-08 | 008-D04 | **O-04 resolved — no attestation enforcement in v1.** Any authenticator (platform or roaming) with attestation format `none` or a self-attestation is accepted; no attestation CA verification, no AAGUID allowlist | Brief O-04 proposed this stance; the user base mixes consumers and firms, and strict attestation is a support burden with no RFI requirement behind it (PLT-05 asks for MFA, not attested hardware) | Require attested hardware keys for org_admins (deferred to a possible future enterprise tier) | Enrollment works with every phone/laptop users already own — the friction goal of this spec. A future tier can tighten via Laragear's format allowlist without schema change | [D] |
| 2026-10-08 | 008-D05 | **The browser ceremony JS is ours** (`resources/js/passkey.js`, a new Vite input): two small flows over `navigator.credentials` with base64url conversions, posting to our routes with the CSRF header. Laragear's vendored JS helper is NOT used | The vendored helper (`resources/js/vendor/webauthn`) is marked deprecated by its own author in favor of a different package (`@laragear/webpass`), and it hardcodes the package's passwordless route shape (`webauthn/login`), which is not our flow | Publish + adapt the deprecated helper (inherits someone else's route assumptions and a deprecation cliff); adopt @laragear/webpass (another dependency for ~120 lines of standard browser API) | passkey.js follows the app's existing per-page JS pattern (document-upload.js, preview-pdf.js): vendored-by-build, no CDN, no new dependency. The server contract (options JSON in, ceremony JSON out) is unchanged either way | [D] |
| 2026-10-08 | 008-D06 | **Passkey challenge completion mirrors Fortify's TOTP completion exactly** — same session keys (`login.id`/`login.remember`), same lockout consultation (`LoginAttemptService`), same bookkeeping on success (clear counters, `last_login_at`, `auth.login` audit with `mfa_used=true`) and on failure (record failure toward lockout, generic surface error). Only the proof differs: a validated WebAuthn assertion instead of a code | The challenge controller, lockout service, and `EnforceSessionPolicies` already encode C-03/C-06 behavior for TOTP; a parallel-but-different passkey path would fork the security posture | Route passkey assertions through Fortify's `TwoFactorLoginRequest::hasValidCode()` (would mean teaching Fortify's request about WebAuthn — forking framework behavior, against the 001-D01 "wire, don't fork" rule) | One challenge page, two proofs, one posture. `EnforceSessionPolicies` needs no passkey-specific login handling — the Login event it already listens for fires from the guard login in the passkey controller too | [D] |
| 2026-10-08 | 008-D07 | **User verification is required** for both ceremonies (`secureRegistration()` / UV=Required on assertion options): the authenticator must prove the *user* (biometric/PIN), not mere device presence | A passkey used as an MFA factor must carry the same assurance as TOTP possession + unlock; tap-only roaming keys without UV would reduce the factor to "has the key" | UV preferred/discouraged (weaker assurance, marginally fewer prompts) | Platform authenticators (the target UX) always do UV. Tap-only legacy keys can't serve as the factor — acceptable: TOTP remains for those users | [D] |
| 2026-10-08 | 008-D08 | **Revocation deletes the credential row** (after password confirmation), audited as `mfa.passkey.revoked` with the label. Deletion is of the user's OWN credential only, scoped by ownership in the route | [D] |
