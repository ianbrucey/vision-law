**009-D04 [D] — O-03: opt-in ethical wall added (archaeology EXTEND).** `matters.restricted` boolean, default `false`. When true: the org-admin org-default branch is skipped in `AccessControl::effectiveMatterRole()` **and** `Matter::scopeAccessibleBy()`; direct/team grants work exactly as before. **009-D05 [D] — O-04: holiday calendars are versioned in-repo data packs.** JSON packs under `database/data/holiday-calendars/` (one file per jurisdiction-year-version), loaded by an idempotent seeder command into `holiday_calendars` + `holidays` tables stamped with pack name/version/checksum; historical versions are retained (new pack = new version rows, never edits). Emergency closures arrive as a new pack version. v1 packs: `us-federal-2026` and `ga-state-2026`, both labeled DEMONSTRATION data. Engine verdicts run against fixture packs, so code correctness never depends on production data quality.

**009-D06 [D] — O-05: hard deadlines and escalations are never digested.** Digest mode batches only noncritical update notices. Mandatory policy notifications (hard-deadline reminders, escalations) bypass digest **and** quiet hours; the org-level floor cannot be configured away by user preferences. C-11's test pins this.

**009-D07 [D] — O-06: blueprint NFRs are recorded, not adopted as claims.** p95/availability targets are aspirations noted for the ops view design (no verdict asserts them). **RPO ≤ 15 min / RTO ≤ 4 hr are infrastructure commitments outside this app's scope** — they require a separate infrastructure decision and are explicitly NOT accepted by this spec. No claim, test, or freeze line may cite them as satisfied.

**009-D08 [D] — O-07: production runtime + email gating.** Install and enable two systemd units on the dev server: `visionlaw-worker` (`queue:work database`) and `visionlaw-scheduler` (`schedule:work`), both restarting on failure and starting after the web service; verify live by dispatching a real reminder job end-to-end. Email channel: coded as a Mailable behind `config/calendaring.php` key `email_enabled` (env `CALENDARING_EMAIL_ENABLED`, **default false**). While disabled, a due email delivery is ledgered `failed_unconfigured` with the reason visible on the ops view — loud, never fake-sent, never silently dropped (brief O-07). In-app delivery is the guaranteed channel. Verdicts behave identically under sync (tests) and database (prod) queue drivers.

## Design decisions the claims require

**009-D09 [D] — One item table.** `calendar_items` carries deadlines, events, and tasks (`type` enum). Unified agenda, search, counts, and feeds are then one scoped query — the C-01/C-02 leak surface stays singular and auditable. Task-only structure lives in satellite tables (`task_dependencies`, `checklist_items`, `item_attendees`).

**009-D10 [D] — Item fields.** org_id, matter_id, type, title, description, visibility (`matter` | `restricted_audience` — attendees + matter viewers with grant; external surfaces only ever see explicitly shared items), status (lifecycle: `draft|confirmed|at_risk|completed|superseded|canceled`), task_status (workflow for tasks: `not_started|in_progress|blocked|in_review|completed|canceled`), classification (`hard|soft|internal`, deadlines), jurisdiction (string), due_date (date, legal deadlines), cutoff_time (time, nullable), starts_at/ends_at (UTC instants for timed items), all_day flag, timezone (IANA, originating zone), location, meeting_url, assignee_id (task responsible), escalation_owner_id, reviewer_id, version (integer, optimistic concurrency), supersedes_id / superseded_by_id, source (`manual|template|recurrence`), template_version_id + rule_key + inputs (jsonb) + calc_trace (jsonb) provenance, series_id + occurrence_date + recurrence_rule (jsonb) for recurrence, created_by/updated_by. Every calculated field must be reproducible from stored provenance (C-05).

**009-D11 [D] — Lifecycle law.** Transitions via `ItemService` only: draft→confirmed→(at_risk)→completed; any non-terminal → canceled (reason required); supersede is system/service-driven on recalculation or replacement and links successor↔predecessor; history rows are never updated in place or deleted (supersede writes status + link columns on the old row exactly once, which is a state transition, not a rewrite of its facts — its original dates/provenance stay byte-identical). Only `confirmed` items drive mandatory reminders and dashboard counts (blueprint D-03).

**009-D12 [D] — Hard-deadline guard.** Editing a confirmed hard deadline's date/classification requires a non-empty `reason` (validated in the service, audited with before/after). The explanation endpoint/view renders anchor, rule key + pack version, each calc step, and adjustments from `calc_trace` — for manual items the trace records "manual entry by <actor>" so the explanation is never empty.

**009-D13 [D] — Task law.** One responsible assignee (nullable → triage queue = unassigned, non-canceled tasks across authorized matters). Reassignment writes notifications to old + new assignee (in-app) and audits. Dependencies are finish-to-start edges with cycle detection at write time (DFS over the matter's task graph); moving a predecessor computes downstream impact (list of affected tasks + date deltas) that must be previewed and confirmed before applying (the service exposes `previewImpact()` and `applyMove()`; the UI posts to preview first). Checklists are ordered items with `required` flags; completing a parent with open required items is refused unless an `override_reason` is supplied by a user with matter `edit` authority — both paths audited.

**009-D14 [D] — Recurrence law.** A series is a row set sharing `series_id`; each occurrence is a distinct `calendar_items` row with its own status. Edit scopes: `this` (one row), `following` (this + later unconfirmed/uncompleted occurrences), `series` (the recurrence rule + all future occurrences; past/completed occurrences are never mutated). Occurrences are materialized 12 months forward from the rule (RRULE-lite: freq daily/weekly/monthly, interval, byday, until/count) by `RecurrenceService`; generation is idempotent per (series_id, occurrence_date).

**009-D15 [D] — Reminder policy model.** `reminder_policies`: item_id, version (per-item incrementing), active flag, rules (jsonb list). A rule: `{offset_minutes: int (negative = before, 0 = at, positive = after) | absolute_at: iso, channels: [in_app, email], recipients: [assignee|owner|watchers|attendees|escalation_owner|user:<id>], criticality: mandatory|standard|digest, label}`. Editing a policy creates a new version (old retained); pending deliveries from superseded policy versions are canceled (`superseded`), sent ones are immutable (C-09). Absolute rules keep their instant; relative rules re-resolve against the item's current date.

**009-D16 [D] — Delivery pipeline + ledger.** `reminder_deliveries` is the ledger and the unit of work: policy_id, item_id, recipient_user_id, channel, scheduled_for, idempotency_key (**unique**), status (`pending|claimed|sent|failed|dead|suppressed_no_access|failed_unconfigured|acknowledged|snoozed`), attempts, last_error, provider_ref, sent_at, acknowledged_at/by, snoozed_until, payload snapshot (title at materialization). Flow: `reminders:dispatch` (every minute) materializes due deliveries from active policies of confirmed items → queues `SendReminderDelivery` jobs → the job atomically claims the row (`pending→claimed` conditional update), **re-resolves the recipient and re-checks matter authorization at send time** (lost access → `suppressed_no_access`, nothing sent — C-10), sends via the channel, records result. Channel failure never blocks the other channel (separate ledger rows). Retry: failed sends requeue with exponential backoff (attempts 1..5, delays 1m/5m/15m/1h/4h), then `dead`; admin replay from the ops view resets a dead row to `pending` (audited). Exactly-once rests on the unique idempotency key + the atomic claim: a provider timeout after a successful send still yields one delivered message per recipient/channel because the row can only be claimed once and replays reuse the same key (C-12 fault-injection test).

**009-D17 [D] — Reminder behaviors.** Immediate notices on assignment, material date change, cancellation, confirmation — generated as deliveries with their own keys, body carrying before/after + actor. Digest: noncritical notices for a user batch into one in-app digest delivery per digest window (default daily 08:00 user zone) when the user enables digest. Ack: recipient acknowledges from the agenda/inbox (audited); snooze target must be ≤ due instant unless the user holds matter `edit` (override, audited). Escalation: a mandatory reminder unacknowledged by its escalation deadline creates a delivery to the item's escalation owner (fallback: matter owner) marked as escalation — never digested, never quieted. Quiet hours: per-user window + org minimum floor stored on `reminder_preferences` (user_id, quiet_start, quiet_end, timezone, digest_enabled, digest_time); mandatory traffic ignores both. **Redaction:** any email about a restricted matter (or any matter, for the external channel) carries a neutral subject/body ("You have a new deadline notification in Vision Law") + secure link — never matter title, facts, or item title (C-11 sentinel).

**009-D18 [D] — Template model.** `deadline_templates` (org_id — org-owned catalog; system/demo templates carry org_id of the system org? **No:** templates are per-org; the DEMONSTRATION pack ships as data files + seeder that installs into a chosen org on demand) — simpler and safer: `deadline_templates` has org_id NOT NULL; the demo pack seeder installs the demo template into every org that lacks it, labeled DEMONSTRATION. Fields: name, jurisdiction, court, matter_type, description, status (derived from latest version). `deadline_template_versions`: template_id, version, status (`draft|in_review|published|retired`), content (jsonb: item graph — items with key, type, title template, classification, rule refs, dependencies by key, checklist, reminder policy template), checksum (sha256 of canonical content), maker_id, checker_id (nullable), effective_from/to, published_at. Published = immutable (any edit forks a new draft version — enforced in service + test). Maker-checker: when org policy flag `templates.require_checker` (org settings jsonb, default **true** for the demo fixtures) publish requires checker ≠ maker.

**009-D19 [D] — Rule representation (DSL).** Rules are data (brief [P] anchor). A rule: `{key, label, anchor: <trigger-or-item-key>, steps: [ {op: add_calendar_days|add_business_days|add_court_days, n}, {op: adjust, mode: next_business_day|prev_business_day|next_court_day|none}, {op: set_cutoff, time} ], classification, reminder_policy_ref}`. Evaluation: build the item DAG from template content (items may anchor on trigger facts or other items' computed dates), topological sort (cycle → instantiation warning, never a hang), evaluate steps with the versioned holiday calendar for the item's jurisdiction, apply trigger-day inclusion policy (`exclude` default: the trigger day is day 0), weekend/holiday adjustment, cutoff. Output per item: computed date + full trace (anchor value, each step's in/out, holiday pack name+version, adjustments applied). Same inputs + versions ⇒ byte-identical trace on replay (C-15).

**009-D20 [D] — Instantiation.** `template_instantiations`: org_id, matter_id (nullable until confirm creates/links the matter), template_version_id, idempotency_key (unique, client-supplied or server-generated per preview session), inputs (jsonb: trigger facts), preview (jsonb: computed graph + warnings), status (`previewed|confirmed|rolled_back`), created_by, confirmed_at. Preview computes without writing items. Confirm runs in one DB transaction: creates items in draft→ then confirms per template default, stamps provenance (template version, rule keys, inputs, traces) onto every item, stamps matter.template_id/version; any failure rolls the whole graph back. Double-confirm with the same key returns the existing graph (C-14).

**009-D21 [D] — Recalculation.** Triggered by trigger-fact change, rule-pack version change, or holiday-pack version change on a confirmed instantiation. Produces an impact comparison (per item: old date → new date, changed/unchanged, manual-override flags) stored on a `recalculation` record (instantiation_id, changes jsonb, status `proposed|approved|rejected`, decided_by/at, applied selection). Nothing mutates until an authorized reviewer (matter `edit`) approves all or a selection; applying supersedes affected generated items (successors carry new dates + traces + provenance pointing at the recalculation), preserves manual overrides unless the approval explicitly includes `reset_overrides`, reschedules reminders via policy re-resolution, and notifies affected assignees/watchers (C-16).

**009-D22 [D] — External coordination (Phase A).** 
- *ICS export:* `GET /calendar/export.ics` (auth) — the caller's authorized items in a window, one VEVENT per item, UID `<item-uuid>@vision.justicequest.pro`, SEQUENCE = item version.
- *Invites:* for selected items, `IcsService::invite()` produces a Mailable with a `REQUEST` .ics (organizer = acting user); update re-sends same UID with SEQUENCE+1; cancel sends `CANCEL` with SEQUENCE+1 (C-17 lifecycle test drives the service + Mail::fake).
- *Feed:* `calendar_feeds` per user (token hash stored, plaintext shown once at issue, revocable); `GET /calendar/feed/{token}.ics` unauthenticated-by-session but token-gated, content = that user's authorized items **re-filtered at fetch time**; revoked/unknown token → 404 with no existence signal.
- *Guest view:* `guest_shares` (org_id, matter_id, guest_email, guest_user_id nullable, item_ids jsonb — explicit item selection, token hash, expires_at, revoked_at). Guest surface `GET /guest/{token}` shows only the shared items' shared fields (title, dates, status — never internal notes, watchers, hidden attendees, description marked internal). Revocation is immediate for web + feed + future reminders; historical ledger rows stay (C-17).

**009-D23 [D] — Time-zone law (C-18).** Timed items: `starts_at`/`ends_at` stored UTC; `timezone` stores the originating IANA zone; display converts to the viewer's zone; ICS export emits UTC instants. Legal deadlines: `due_date` is a date in the matter's jurisdiction zone — it never shifts with viewer zone; reminders for date-only deadlines resolve in that zone (cutoff time local). DST: reminder materialization computes the UTC instant from local date+time+zone via Carbon, so a 9:00 AM America/New_York reminder fires at the correct UTC instant on both sides of a transition, exactly once (idempotency key includes the resolved instant).

**009-D24 [D] — Audit event set (C-19).** `calendar.item.created|updated|confirmed|completed|canceled|reopened|superseded`, `calendar.task.assigned|completed|reopened`, `calendar.task.dependency_changed`, `calendar.task.checklist_overridden`, `calendar.reminder.acknowledged|snoozed|escalated|replayed`, `calendar.template.created|submitted|published|retired`, `calendar.instantiation.previewed|confirmed`, `calendar.recalculation.proposed|applied|rejected`, `calendar.export.performed`, `calendar.feed.issued|revoked|accessed` (access logged without the credential — payload carries feed id only), `calendar.guest.invited|revoked`, `matter.restricted.changed`. Payloads carry before/after + reason where the brief requires, actor, and request id where available; the AuditLogger blocklist shapes key names (no `token`/`secret`/`hash` substrings).

**009-D25 [D] — Home module (010-D08).** `HomeController` assembles, over the caller's accessible matters only: next 5 upcoming confirmed deadlines/tasks (due asc), overdue count, items due within 7 days count, unacknowledged mandatory reminder count; `home.blade.php` renders a "Deadlines & agenda" card below Recent activity with a link to `/calendar`; the zero-matter guided empty state is untouched (module hidden when the user has no accessible matters — 010 C-04 verdict preserved).

**009-D26 [D] — Agenda filters persist per user** in `reminder_preferences`-sibling table `calendar_filter_preferences` (user_id, filters jsonb: matter ids, types, statuses, assignees, window) — applied server-side on every agenda read (C-02).

## Security matrix additions (new cells the tests pin)

- org_admin × restricted matter without grant → 404 everywhere (items, agenda, counts, search, export, feed, home module).
- org_admin × restricted matter **with** grant → normal role behavior.
- outside_counsel (guest principal) × shared items → shared fields only; × unshared items of the same matter → nothing.
- Any user × other org's items → 404 / empty, including via feed token of a user whose access was revoked.
- Recipient who lost access between materialization and send → suppressed, zero channel sends.
